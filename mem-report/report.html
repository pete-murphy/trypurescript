trypurescript server peak heap: three package-set scenarios

Peak heap (maxLive = “bytes maximum residency” from +RTS -s) of the trypurescript server booting three package sets, each measured cold (no staging/.psci_modules/ cache) and warm (cache present from the same scenario's cold boot). Warm boot is the memory-worst case: deserialising per-module externs.cbor files loses the sharing the typechecker's in-memory structures have. All runs: same release binary (GHC 9.2.5), +RTS -N2 -A128m -M<cap> -S, one successful /compile before clean SIGINT exit; local Apple-silicon hardware (droplet boot times will be slower; memory numbers transfer). Production (deploy/start) runs with -M3G on a 3.8 GiB droplet, so “warm maxLive < 3,072 MiB” is the go/no-go line. Verdict: full does not fit, trim-current fits, trim-cannot-run fits under -M3G warm.

Live heap over time (major GCs only)

Post-collection live bytes at each major GC, from the -S traces of the -M8G runs. Cold boots peak early during typechecking and decline; warm boots climb while deserialising externs and plateau at their peak until the first request. MiB vs elapsed seconds.

How to reproduce

# from the repo root, branch mem-report (needs stack-built server binary + spago 1.x)
for scen in trim-current trim-cannot-run full; do
  mem-report/measure.sh "$scen" cold 8G   # also populates .psci_modules for the warm runs
  mem-report/measure.sh "$scen" warm 8G
  mem-report/measure.sh "$scen" warm 3G
  rm -rf staging/.psci_modules            # never reuse a cache across scenarios
done
python3 mem-report/make_report.py

Scenario package sets live in mem-report/scenarios/<name>/spago.{yaml,lock}. trim-cannot-run = the full set minus the 148-package “cannot run in the playground” closure (mem-report/cannot-run.json, regenerable via make_cannot_run_yaml.py). Raw per-run data: mem-report/results.json.
